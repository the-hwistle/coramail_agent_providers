# DECISION-002 Qdrant를 벡터 검색 저장소로 사용

## 상태

채택

---

## 맥락

CoRA Mail Agent는 이메일 본문, 첨부파일 텍스트, 과거 대화, 유사 요청을 검색해야 한다.

키워드 검색만으로는 짧은 답장, 표현이 다른 문의, 첨부파일 중심 요청, 과거 발주와 연결된 문맥을 찾기 어렵다. 벡터 검색은 의미적으로 가까운 메일과 첨부파일을 찾는 데 필요하다.

---

## 결정

Qdrant를 이메일과 첨부파일의 벡터 검색 저장소로 사용한다.

PostgreSQL은 원본 데이터와 업무 상태를 저장하고, Qdrant는 검색용 벡터와 검색 필터에 필요한 payload를 저장한다.

---

## 근거

- Qdrant는 vector와 payload를 함께 저장하는 point 구조를 제공한다.
- payload filter를 사용해 기간, 발신자, 업무 유형, 첨부파일 여부 같은 조건을 검색에 결합할 수 있다.
- payload index를 통해 자주 필터링하는 필드의 검색 성능을 관리할 수 있다.
- 컬렉션 단위로 임베딩 모델과 벡터 차원을 분리하기 쉽다.
- 로컬 개발과 데모 환경에서 시작하기 쉽고, 운영 확장 시에도 구조를 유지할 수 있다.

---

## 대안

| 대안 | 판단 |
|---|---|
| PostgreSQL pgvector | PostgreSQL 안에서 벡터까지 관리할 수 있지만, 벡터 검색과 payload 기반 필터링을 독립적으로 운영하려는 현재 구조에서는 Qdrant가 더 명확하다. |
| Elasticsearch/OpenSearch | 키워드 검색과 로그 검색에는 강점이 있지만, 이 프로젝트의 초기 핵심은 이메일·첨부파일 의미 검색이다. |
| Chroma | 로컬 실험은 쉽지만, payload filtering과 운영 확장 관점에서 Qdrant를 우선한다. |
| 벡터 저장소 미사용 | 과거 메일 문맥 검색, 유사 요청 검색, 첨부파일 기반 검색 요구를 충족하기 어렵다. |

---

## 영향

- 이메일 컬렉션과 첨부파일 컬렉션을 분리한다.
- Qdrant payload에는 검색 필터와 원본 연결 식별자만 저장한다.
- 이메일 본문 전체는 PostgreSQL을 기준으로 관리한다.
- 임베딩 모델이 바뀌면 새 컬렉션을 만들고 재색인한다.
- PostgreSQL에 Qdrant index record를 저장해 원본과 point 연결을 추적한다.

---

## 변경 판단 기준

- 운영 환경에서 별도 Qdrant 운영이 부담으로 확인된다.
- 검색 요구가 키워드 검색 중심으로 축소된다.
- 고객 인프라 정책상 별도 벡터 DB 운영이 제한된다.
- pgvector만으로 충분한 검색 품질과 운영 편의성이 확인된다.
