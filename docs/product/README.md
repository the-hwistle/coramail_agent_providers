# CoRA Mail 제품 정의

## 문서 목적

이 문서는 CoRA Mail이 어떤 문제를 해결하는 제품인지, 초기 구현 범위가 어디까지인지, 기능과 아키텍처 문서가 어떤 기준으로 작성되어야 하는지를 정의한다.

CoRA Mail Agent는 제품 요구 사항, 데이터 흐름, 서비스 경계, 관찰 가능성, 평가 체계를 문서로 먼저 정의한 뒤 단계적으로 구현한다.

이 문서는 다음 작업의 기준으로 사용한다.

- 기능 우선순위 결정
- 사용자 시나리오 작성
- 데이터 스키마 검토
- API 계약 정의
- Agent, Tool, Service 책임 분리
- 테스트와 평가 데이터 구성
- 웹 화면과 API 계약의 책임 범위 판단

---

## 제품 한 줄 정의

CoRA Mail은 업무 메일과 첨부파일을 수집, 분석, 분류, 검색, 라우팅하여 사용자가 중요한 요청과 후속 조치를 빠르게 파악하도록 돕는 온프레미스 AI 메일 업무 지원 시스템이다.

---

## 해결하려는 문제

업무 메일은 견적, 발주, 기술 검토, 클레임, 서비스 요청 같은 실제 업무의 시작점이다. 많은 조직에서는 다음 문제가 반복된다.

- 메일 본문과 첨부파일을 사람이 직접 열어야 업무 유형을 알 수 있다.
- 짧은 본문과 긴 첨부파일이 함께 있을 때 핵심 요청을 놓치기 쉽다.
- 문의, 발주, 클레임처럼 후속 조치가 다른 메일이 같은 받은편지함에 섞인다.
- 담당자 배정 기준이 사람의 경험에 의존한다.
- 긴급 메일과 실패한 AI 분석 결과를 명확히 구분해야 한다.
- AI 판단 수정 결과를 평가 데이터와 개선 흐름으로 연결해야 한다.
- 프롬프트, 모델, 검색 설정 변경의 효과를 재현하고 비교하기 어렵다.

CoRA Mail은 메일 자동 처리, 사람 검토, 사용자 수정을 하나의 업무 흐름으로 연결한다. AI 판단은 업무를 빠르게 시작하기 위한 제안으로 저장하며, 확신도가 낮거나 근거가 부족한 결과는 사람 검토 대상으로 전환한다.

## 핵심 업무 객체

CoRA Mail의 제품과 데이터 모델은 다음 객체를 중심으로 설계한다.

| 객체 | 설명 |
|---|---|
| 이메일 계정 | 수집 대상 메일함과 공급자 연결 정보를 나타낸다. |
| 이메일 메시지 | 수신 또는 동기화된 원본 메일 단위다. |
| 이메일 스레드 | 같은 대화 맥락에 속한 메일 묶음이다. |
| 수신자 정보 | To, CC, BCC 등 메일 주소별 역할을 나타낸다. |
| 첨부파일 | 메일에 포함된 파일의 메타데이터와 저장 위치를 나타낸다. |
| 첨부파일 분석 결과 | 문서 유형, 추출 필드, 표 구조, 분석 실패 상태를 저장한다. |
| 업무 분류 | 문의, 발주, 기술 검토, 클레임 등 업무 유형 판단 결과다. |
| 담당자 라우팅 | 메일을 처리할 사용자 또는 팀 후보와 확정 결과다. |
| AI 분석 결과 | 요약, 분류, 추출, 근거, 신뢰도, 모델·프롬프트 버전을 포함한 결과다. |
| 사람 수정 기록 | 사용자가 AI 결과를 수정하거나 확정한 이력이다. |
| 처리 작업 | 수집, 첨부파일 분석, 임베딩, 요약, 분류, 라우팅 등의 비동기 작업이다. |
| 검색 인덱스 | Qdrant에 저장되는 이메일 및 첨부파일 검색용 벡터와 payload다. |

## 제품 범위

### 초기 범위

초기 구현은 기능별로 동작을 확인할 수 있는 작은 단위부터 만든다.

1. 샘플 이메일을 저장한다.
2. 받은편지함 목록과 상세 화면을 제공한다.
3. 이메일 본문을 요약한다.
4. 이메일을 업무 유형으로 분류한다.
5. 첨부파일 메타데이터와 분석 결과를 표시한다.
6. 이메일과 첨부파일을 검색 인덱스에 연결한다.
7. 사용자가 AI 결과를 수정하고 검토 완료 상태를 남긴다.
8. AI 실행 로그와 평가 데이터를 축적한다.

### 초기 범위에서 제외

다음 항목은 향후 확장 후보로 관리한다.

- 실시간 다중 메일 계정 운영
- 완전 자동 답장 발송
- 외부 ERP 또는 CRM 직접 쓰기 연동
- 복잡한 조직 권한 체계
- 다국가·다조직 SaaS 운영
- 고가용성 배포 구성
- 모든 문서 형식에 대한 OCR 완성도 보장

## 제품 원칙

### 1. 원본과 AI 결과를 분리한다

메일 원문, 첨부파일 메타데이터, 사용자 수정값, AI 분석 결과는 서로 구분해 저장한다. AI 결과가 바뀌어도 원본 데이터가 변경되어서는 안 된다.

### 2. AI 결과는 재현 가능해야 한다

모든 AI 결과는 프롬프트 이름, 프롬프트 버전, 모델, 생성 설정, 입력 요약, 출력 스키마 검증 결과와 연결되어야 한다.

### 3. 불확실성은 화면과 데이터에 남긴다

확신도가 낮거나 필수 필드가 누락된 결과는 사람 검토 필요 상태로 표시한다. 근거 부족, 분석 실패, 재시도 대기 상태를 구분한다.

### 4. 사람 수정은 개선 데이터다

사용자가 업무 레이블, 담당자, 긴급도, 추출 필드를 수정하면 최초 AI 결과와 수정 결과를 함께 저장한다. 이 기록은 평가 데이터와 회귀 테스트의 원천으로 사용한다.

### 5. 웹은 얇게, 계약은 명확하게 유지한다

화면은 API 계약과 상태 표현에 집중하고, AI 파이프라인 내부 구조에 직접 의존하지 않도록 한다. 화면이 기대하는 데이터는 API 문서와 스키마에 맞춰 명확히 정의한다.

### 6. 기능 단위로 끝까지 구현한다

하나의 기능을 `문서 -> 스키마 -> API -> 서비스 -> 테스트 -> 화면` 순서로 연결해 동작을 확인한 뒤 다음 기능으로 확장한다.

## 성공 기준

초기 버전의 성공 기준은 업무 사용성, 시스템 안정성, 관찰 가능성, 모델 정확도를 함께 본다.

| 영역 | 기준 |
|---|---|
| 업무 효율 | 사용자가 메일 전체를 열기 전에 업무 유형, 요약, 핵심 필드를 확인할 수 있다. |
| 분석 품질 | 주요 시나리오별 인수 기준을 만족하거나 실패·검토 상태로 안전하게 전환한다. |
| 데이터 일관성 | 원본 메일, AI 결과, 사용자 수정, 검색 인덱스 연결이 추적 가능하다. |
| 관찰 가능성 | 메일 한 건의 처리 흐름을 단계별 trace와 job 상태로 확인할 수 있다. |
| 평가 가능성 | 사용자 수정 사례와 고정 평가 데이터로 프롬프트·모델 변경 효과를 비교할 수 있다. |
| 확장성 | 새로운 Agent나 Tool을 추가할 때 웹/API 계약과 원본 스키마의 변경 범위를 통제할 수 있다. |
